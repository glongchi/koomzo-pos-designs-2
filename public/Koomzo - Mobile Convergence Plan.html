Convergence plan · delivered

Mobile into Flex: one register, four compositions

The Mobile register is a fourth parallel implementation, not a view of the others — its own catalogue, its own components, its own stylesheet. But its three phone patterns for the live order are real design work that Flex does not have. This plan moves those patterns into Flex as layout options, retires mobile/, and makes the spec's §9 and §17 true instead of aspirational.

Retail Flex Phone compositions Register spec Change plan

Why this is one register

The same argument as change 11, one layer up.

The money layer is already shared

After the last round, Mobile reads the same tender list, charge phases, ticket numbering, tax function and discount policy as the other three. Nothing about payment is duplicated any more.

The board layer still is

MTile, MCatalog, MTicket, MLine, MEditor, MOrderPanel shadow Flex's Tile, CatalogGrid, Cart, CartLine, KeypadSheet. Two of everything.

And it costs capability

Mobile has no presets, no capability map and no qualifier chain. A phone cannot age-check, take an Rx sign-off, pick a variant, choose a batch, capture a serial or weigh anything — the exact chain the spec calls invariant.

But it earned something

Three genuinely different answers to "where does the live ticket live on a 390 px screen". Flex has one answer — a side drawer. That exploration is what we keep.

The four compositions

Reading your "four" as the four device classes in the spec's §17 — which is what the register must actually survive. The three phone patterns then become a choice within the phone composition, not three more compositions.

Sheet · bar · tab — a tweak

If you meant four patterns rather than four devices, the difference is only whether the side drawer survives as a phone option alongside sheet / bar / tab. My read: it shouldn't — a side drawer on a 390 px screen is a worse sheet. It stays the tablet-portrait answer, where it is correct.

Flex's container queries already do more than the spec credits it with. The delta is smaller than it looks.

Step 1 · Layout CSS

1Three new compositions in rx.css
New CSS
retailflex/rx.css

Add .board.sheet, .board.bar and .board.tabs beside the existing .board.drawer, porting the geometry from mkit.css — .m-sheet (bottom sheet + grab handle + scrim), .m-orderbar (72 px bar, 46 px cart glyph, 48 px go button) and .m-tabs (40 px segmented strip).

Translated into Flex's class names, so the cart stays .cart and the ticket lines stay .line — no second vocabulary enters the file. All three are container-query-scoped so they only apply at phone width, and the bottom offsets account for the rail already sitting at the bottom under 640 px.

Step 2 · Order bar and tab strip

2Upgrade DockBar, add TabStrip
Components
retailflex/rx-parts.jsx

DockBar gains the cart glyph and count badge from MOrderBar — it already takes count, it just doesn't show it. A new TabStrip component renders the catalogue / order pair with the badge.

The Cart component itself is unchanged: it already renders head, customer row, lines, totals and the pay bar, and it is what the sheet, the drawer and the tab view all show. One ticket component, four places to put it.

Step 3 · The tweak

3Layout becomes composition, device gains a value
Tweaks
retailflex/rx-app.jsx

Today: layout: right | drawer and device: desktop | tablet | phone.

After: device: desktop | tabletL | tabletP | phone, and a phoneOrder: sheet | bar | tab tweak that appears only when device is phone — exactly Mobile's control, in Flex's panel. layout keeps cart right / cart drawer for the desk and tablet cases, because that is a real preference a shop has at a counter.

The board class then composes as board + (phone ? phoneOrder : layout), and the existing transient-state reset on device change comes across from m-app so switching pattern never leaves a sheet half-open.

Step 6 · The spec gains a section

6§20 · One register, four compositions
New section
Koomzo - Register Functional Spec.html

You left this to me, so: a new section rather than a rewrite of §9. The existing §9 stays as the Mobile module's record — it describes what was built and why the phone patterns exist — and the new section states the resolved architecture: one register, four device compositions, three phone patterns as a tenant choice, and the rule that follows from it.

Three smaller edits go with it: §5's capability matrix loses the Mobile column and gains a compositions row; §9's heading is marked merged into Flex; and §17's device table gets the phone-pattern choice named rather than implied. The four-module framing in the opening lede becomes three.

What does not move

Deliberate losses, each with a reason — this is the part of a convergence worth arguing about.

DroppedWhy
KZ_PRODUCTS / KZ_CATEGORIESMobile's generic catalogue. Flex's per-preset catalogues are richer and carry the qualifier flags (weighed, variants, serial, Rx, lot) that make the entry chain work. Keeping both is the duplication we are removing.
MTile, MLine, MTicket, MOrderPanelStraight duplicates of Flex components. Flex's versions already handle variants, batches, serials and weights on a line; Mobile's cannot.
MEditorMobile's inline numpad. Flex's KeypadSheet does the same job and now carries the discount ceiling and the approval step, which Mobile's does not.
The device switcher chromeMobile's scaled device stage with a phone / tablet / tablet toolbar. Flex already scales to a device preset through its own tweak; two preview mechanisms is one too many.
+/− numpad keyA negative quantity is not a thing on a ticket — a return is a return. It was never right.

Risks

RiskHandling
Bottom-chrome collisionUnder 640 px Flex already puts the module rail at the bottom (58 px) and the dockbar above it. A sheet, a tab strip and an order bar all want that space. Each composition gets explicit offsets, and I will screenshot all three at 390 px before calling it done.
The qualifier chain on a phoneFlex's sheets become bottom sheets under 640 px already, so the chain should work — but it has never run at phone width with a real preset. Pharmacy (Rx → variant → batch) is the worst case and the one I will test.
Losing the demo value of MobileMobile's page is a presentation artifact: three phone patterns side by side in a device frame. Inside Flex they become one tweak you change to compare. If showing them together matters, that is a canvas of three Flex frames, and worth saying now rather than after the delete.
Tweak-state churnRenaming device values invalidates any saved tweak state on the Flex page. Harmless, but the page will open at its defaults once.
