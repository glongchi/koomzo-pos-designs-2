Purpose

Written from the interface inward

Every screen states what it reads, what it writes, and which rules hold even when a client misbehaves — so services can be built against it without guessing.

One source of truth

The document renders from data. Adding a module or refining a screen is a data edit, not a layout edit.

Contract, not wishlist

Entities, rules, events and endpoints per module. Open questions are named rather than assumed away.

Living to ship

Nothing here is final until its module ships. Sections mature as modules are designed and refined.

Platform

Design goals

These hold for every module. A module that violates one is wrong, not innovative.

One shell, one rail, every module

A module fills the surface it is given and lands on its own core screen. Learning one module's navigation is learning all of them.

One product, one data model

Every install ships every capability. Setup decides what the operator meets — nothing is compiled out or licensed separately.

The transaction is sacred

No plan limit, sync failure or configuration change may block a sale, a kitchen ticket or an appointment. Degrade reporting; never interrupt trade.

Nothing changes state silently

Every quantity, tender and configuration change is an appended record with an actor and a timestamp. Corrections are new records.

Modules compose, never duplicate

A new trade is a new configuration of existing objects plus the few it genuinely lacks. Two modules may never own the same object.

Attention is computed, never pushed

Badges and counts are projections of the event stream. If nothing is waiting, nothing is shown.

Platform

Capability resolution

Effective visibility passes through four stages. Each stage may only subtract — implemented once, server-side, and mirrored by the client.

01

Plan ceiling

What the tenant's plan can ever expose. Overage notifies; it never blocks a sale.

02

Tier & switch

off · lite · mid · full, plus per-capability switches the operator sets in Setup.

03

Role

owner · manager · staff, immutable for the session.

04

Device

Register, KDS, kiosk, display, tablet, phone. Some capabilities are device-scoped.

A hidden capability must reject its own endpoints with 409 CAPABILITY_DISABLED — not merely be unreachable in the UI.

Platform

Rules the server enforces

1Winding, not off. A capability holding open obligations cannot go straight to off. Documents go to winding; money is hard-blocked until reconciled or a variance is recorded with an owner PIN and reason.
2History is annotated, never invented. enabled_from is set once and never cleared. Reports start a series where the data actually starts.
3Every write is idempotent. Writes carry a client-generated key; replays return the original result, not a duplicate.
4No floats on the wire. Money and quantity are integers in minor units. Zero-decimal currencies carry an exponent of 0 — the minor unit is the franc.
5One posting, never a copy. A charge raised in one module and settled in another is a single posting with a source module; the originating document stays immutable.

Platform

Badges are projections, not notifications

DerivedA count of work waiting on the signed-in person today, on that screen. Absent at zero, capped at 99+.
Event-drivenA domain event names the rules it dirties; the projector recomputes only those. Folding the same event twice changes nothing.
Resolved firstIf the capability behind a rule is off, locked or out of role, the rule is never evaluated and no counter is returned.
ScopedA housekeeper's count is her own rooms; a manager's is the property's. Two people on one rail may see different numbers.
Never the routeAnything countable must also be reachable by navigating. A badge is an accelerator, not a channel.
EndpointContract
/v1/attentionEvery counter visible to the caller, already resolved and scoped. Also on bootstrap, so a cold start paints badges.
/v1/attention/streamServer-sent attention.changed. The client patches one counter; it never re-polls the set.
/v1/attention/rulesThe catalogue with each rule's enabled state — drives the Setup toggles.
/v1/attention/recomputeAdmin-only cold rebuild from the event log. Must produce identical counts.

Foundations

Two engines under every module

Forms

One authoring surface for every question a business asks itself — opening checks, incident reports, wholesale applications — and one place the answers land. Multi-step logic, authored data sources with schema and offline policy, and two parent-child rules: visibility and option filtering. Hidden fields save no answer.

Automations

The rules a business would otherwise keep in somebody's head: when this happens, do that — authored as recipes, watched as runs. The irreducible job is seeing what runs by itself and being able to stop it; branching, webhooks and human approval steps switch on with scale.

Both engines read the same event stream every module emits, so a new trigger costs a rule rather than a service.

Module

Gym & Wellness

A members' club is a gate and a schedule. The irreducible job is the gate: is this person allowed in, right now.

Front desk

Offline-first admission. Member state is cached, one resolver decides, renewals get a grace period, and refusals queue locally.

Members & plans

Billing cycles, freezes and packages. Admission is append-only; occupancy and balance are projections.

Classes

Timetable, capacity and trainer assignment, with commissions settling on the shared objects.

Assets

Lockers by bank — prefix plus range, retired or active. Equipment tracks service intervals and overdue status.

A telecom outage never locks a paying member out. The device decides; the server reconciles.

Design goal 5 — the transaction is sacred

Behaviour

Offline is the normal case

Registers, kitchen displays, kiosks and the gym gate keep working through an outage and reconcile on reconnect.

Decide on the device

Cached state plus one resolver, so admission and tender do not wait on a round trip.

Queue and replay

Writes carry a client-generated idempotency key. Replays return the original result.

Server stays authoritative

The client mirrors the rules for responsiveness; the server re-resolves and enforces on every write.

Before build

Open questions

Turnstile hardware scopeDoes the gym gate drive physical hardware in v1, or does the front desk stay the only enforcement point?

Rotating or static member QRA static code is offline-trivial and shareable; a rotating one needs a clock the device may not have.

Capacity at the gateHard refusal when a class or floor is full, or a receptionist hold that a manager can release?

Mobile-money priorityWhich providers integrate first, and does settlement confirmation arrive by callback or by poll?

Next

Close the questions, then build the services

The specification is stable enough to implement against. Each module section is independently buildable; the platform resolver and the event bus are the shared prerequisites.
