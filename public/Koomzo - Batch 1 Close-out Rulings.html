Three decisions were waiting on me, and two of them already have a precedent in the source code that settles them. Below: the three rulings, the mock-backend contract for everything in the backend phase, and a recommended order for the rest — weighted for a Douala operator on a Bluetooth thermal printer and an intermittent connection, not a European venue with a channel manager.

1 · Void after fire — agreed, and there is already a precedent

Ruled: restore the unit, then write it off. Two movements, net one. Your recommendation, and it is the pattern the codebase already uses.

kz-stock-sales.js:70 reverseSale() already does exactly this for damaged returns, with a comment stating the intent: damaged goods are two events — the customer's refund, and the business's write-off. It posts the refund as kind:'sale' and the write-off as kind:'adjust', reason:'damaged'.

A dish voided after firing is the same shape: the kitchen consumed it, then the business threw it away. So the fire adapter mirrors the method rather than inventing one.

Today — 30 → 28
fire −1 kind:'fire' void −1 kind:'fire' ← wrong counted twice
Ruled — 30 → 29
fire −1 kind:'fire' void +1 kind:'fire' reason:'void-reversal' −1 kind:'adjust' reason:'waste'

Three rows, not two, and deliberately so: the fire stays on the record, the reversal cancels it, and the waste is the number an owner can actually act on. It also keeps rung 4 variance honest later — waste is attributable, not hidden inside a depletion figure. One method (reverseFire()) and one spec paragraph, as you said.

One rider. A void before fire still posts nothing — no consumption happened. The rule only engages once firedAt is set.

2 · Gym and restaurant stock — each gets its own site

Ruled: two new rows in IV_LOCATIONS. Agreed with you — and the current state is worse than a fixture shortcut, it is a reporting falsehood.

Today IV_LOCATIONS holds dt · Akwa Boutique (Store), up · Bonapriso Salon (Salon), plus warehouse and a fourth site. Posting the gym bar to up means the salon's stock report shows energy drinks it never sold; posting the restaurant cellar to dt puts wine on the boutique's valuation. Every location-scoped surface — count sheets, transfers, reorder, valuation, variance later — inherits that error. A cycle count at Bonapriso would come back short by exactly the gym's consumption, and nobody would know why.

Each location row already carries kind, code, sells, staff, icon, so the addition is declarative:

{ id:'gy', name:'Akwa Fitness Bar', kind:'Gym', code:'GF', sells:true, icon:'barbell-outline' } { id:'rk', name:'Le Comptoir Cellier', kind:'Restaurant', code:'LC', sells:true, icon:'restaurant-outline' } // then GM_LOC = 'gy' RK_LOC = 'rk'

Two extra rows in every location selector is the correct cost — a multi-site operator in Douala running a salon, a gym and a restaurant off one Koomzo account is precisely the target customer, and they need to see three separate stock positions. Update the fixtures in the same commit so the seeded movements land on the right sites; as you say, the tests are not the blocker.

4 · The backend phase — mock service contract

Your instruction, made concrete: an interface plus a mock implementation plus JSON-file persistence, so koomzoapps swaps the implementation and nothing else.

The rule for these seven hotel buttons and the gym WhatsApp action is not "stay absent until a real connection exists" — it is "call a real interface whose implementation happens to be a mock." That difference matters: the Angular component, the loading state, the error state, the disabled state and the success toast all get built and tested now, and production only replaces one provider.

// koomzodesignsystem/src/app/core/backend/ export interface PrintService { printFolio(folioId: string): Promise<PrintJob>; // PrintJob: {id,status,at} } // mock/print.mock.ts — resolves after a realistic delay, writes to // backend/data/print-jobs.json, and can be told to fail. providers: [{ provide: PrintService, useClass: MockPrintService }]

Three properties every mock must have, because they are what the UI is being built against:

  • Latency. 600–1500 ms, not instant. A Douala connection is not instant, and a button with no spinner state ships broken.
  • A failure path. A settings toggle or a seeded item that always fails. Offline is the normal case here, not the edge case — the retry and queue states are the feature, and they cannot be designed against a mock that always succeeds.
  • Durable state. Written to JSON under backend/data/, so a sent WhatsApp link is still sent after a reload and the history views have something real to render.

Build one OutboxService the four sit on rather than four retry implementations. This is the single highest-value piece of the backend phase for this market.

Item 9 — reload survival, and the line that must not be crossed

Ruled: one register-wide persistence rule. Persist the order. Never persist the tender result.

You are right that this is one decision for every register, not a restaurant fix. It is also the highest-priority item on this entire list: power cuts and browser reloads are routine in this market, and a register that loses an open table on reload is not deployable. But it collides directly with the money-loss defect found earlier, where a reload re-hydrated a previous order's succeeded tenders and could charge a room twice. So the rule has to be two-sided:

Persist — survives reload
open tables · cart lines · qty modifiers · seat/course · notes customer · discount (unapproved) ticket no (session-scoped seq)
Never persist — rebuild or discard
succeeded tenders MoMo pending state folio post confirmations supervisor approval grants

Mechanically: one RegisterStateService writing to localStorage under kz:register:<locId>:<registerId>, debounced, versioned with a schema number, and cleared on Z-close. On load it restores the order and shows a quiet "Restored your open orders" line. A tender bucket found on load is validated against ticket identity and total before it is trusted, and discarded otherwise — that validation is the fix for the double-charge, and it belongs in the same commit as the persistence, never after it.

Do not ship persistence without the tender validation. Persistence alone makes the money bug easier to hit, not harder.

7 · Item 26 — the floating pay bar

Ruled: fix it, but not now — schedule it as a single contained change after the shell pass, not as a retail patch.

A pay bar that floats mid-screen on a 768 px portrait tablet is not cosmetic: the portrait tablet is a very common register form factor in this market, and the Charge button is the one control that must be in the same place every time. Muscle memory is the whole argument for a pinned bar.

But you are right that it touches all five retail layouts, so do not patch it inside another task. The fix is to make the bar a sticky footer of the order-panel container with a min-height on the scroll region above it, so a short product list still pushes it down — one shared container change, applied five times, tested at 768 px portrait specifically. Keep the KNOWN-GAP entry in FROZEN.md until it lands.
