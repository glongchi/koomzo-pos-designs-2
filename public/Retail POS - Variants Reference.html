Variants across retail profiles

A working definition of “variant” for the Koomzo register, and how the concept changes shape in each business type. This is the reference for the overrides-layer build (profile presets + per-feature toggles).

What a variant is, practically

Merchants and vendors use the word loosely. For POS purposes only one definition matters, because only one has consequences at the moment of the tap.

A variant is a sellable, separately-stocked version of one product concept that shares its name, price logic and reporting line — but must be identified before it can enter the ticket.
It has its own stock

Medium Sand is in or out of stock independently of Large Black. If stock is shared, it isn’t a variant.

It has its own barcode/SKU

Each variant scans to a unique code. Scanning bypasses the picker entirely — the code already resolves the choice.

It reports as one product

The merchant wants to see “Linen Shirt: 48 sold”, then break it down by size — not 15 unrelated products.

It blocks the sale until chosen

The cashier cannot complete the line without picking. That’s what earns a variant its own step in the UI.

Variants
  • Size × colour — Linen Shirt · M · Sand
  • Volume/pack — Shampoo 100 ml / 300 ml / 1 L
  • Strength × form — Ibuprofen 200 mg tablet / 400 mg capsule
  • Capacity × finish — Phone 128 GB Graphite
  • Length/gauge — Cable 1.5 mm² / 2.5 mm²
Not variants — different mechanisms
  • Weight — 0.842 kg is a measured quantity, not a version → scale step
  • Serial number — identifies one unit, not a version → serial capture
  • Modifiers — oat milk, gift wrap: price add-ons with no stock → modifier step
  • Batch / expiry / lot — traceability on the same variant → lot capture
  • Bundles & kits — a set of separate products → kit expansion
Design consequence: the four right-hand mechanisms are often mislabelled “variants” in requirements documents. Keeping them separate is what lets one register serve every profile — each is an independent toggle that inserts its own step between tap and ticket, and a profile is just a preset combination of them.

What this means for the build

Reading down the “Also needs” column: no two profiles want the same set, but every cell is one of eight reusable steps. That is the architecture for the overrides layer.

Picker shape is a setting

none · single · matrix · swatch · configurator. Grocery and fashion both have variants; only one should ever see a grid.

Axes are named per profile

The same UI renders “Size × Colour” or “Strength × Form × Pack”. Labels come from the profile; the component does not care.

Steps compose in a fixed order

Age → Rx → variant → lot → serial → weight → modifiers. A profile enables a subset; order never changes, so cashiers build one muscle memory.

A scan always wins

If the barcode resolves to a variant, skip its step. This single rule is why a scan-first grocery lane and a matrix-heavy boutique can share one register.
